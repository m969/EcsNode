# （单位派遣）模块功能设计文档

## 设计范围说明
基于《需求文档》中的当前条目，仅对以下能力进行细化：
1. 单位注册 / 注销（需求只显式写了单位注册，任务保持最小占位描述，不扩展新能力）。
2. 分配与再分配：支持“即时”与“批处理（逐帧或定时）”两种触发方式。只讨论调度策略的抽象，不引入具体复杂算法实现细节。
3. 结果输出：已分配 / 取消分配事件；以及面向外部系统的查询接口（仅自然语言描述其语义）。
4. 不涉及：寻路、战斗、动画、移动执行、外部任务生命周期管理等（保持边界纯粹）。

## 设计原则（与需求对齐）
- 简单：核心只做“选择谁去哪里”，不把执行行为塞进来。
- 稳定：调度频率与批处理规模可控，避免抖动与过度重算。
- 可扩展：策略/过滤条件/优先级的变化通过配置与策略抽象层承载，而非在流程中硬编码分支。
- 消除特殊情况：未注册对象不参与循环；空集合直接返回，无额外标记位。

## 一、配置设计

围绕“调度频率”“触发方式”“策略选择”三大类配置。所有配置都应允许外部模块在初始化阶段一次性提供；运行期仅支持显式调用接口修改（不做隐式热更新）。

1. 调度触发模式配置
	- 即时分配：当有新单位注册、单位可用状态变化、或外部显式请求时立即进行一次调度尝试。适合数量较少或需要低延迟反馈的场景。
	- 批处理分配：以固定间隔（帧间隔或时间间隔）统一处理积累的“待调度变更集”。适合高并发单位，减少重复计算。
	- 两种模式可同时启用：即时用于“快速补缺”，批处理用于“全局再平衡”。

2. 调度频率相关配置
	- 批处理间隔：以“帧数”或“秒”之一形式设定（二选一，避免双重基准）。
	- 单次批处理最大处理量（可选）：用于限制每个批次重新评估的单位/任务上限，控制尖峰成本。若未配置或为非正值则视为不限制。

3. 策略抽象层配置
	- 仅抽象为“策略标识”与“策略参数集合”。模块内部不硬编码具体策略名，不内置算法描述，避免超出需求范围。
	- 支持外部在初始化时声明“默认策略”，以及为特定分类（例如任务类型或岗位类型）注册“策略覆盖”。
	- 若找不到覆盖策略，回落到默认策略；若无默认策略，分配流程对相关条目直接跳过（不报错，不记录特殊标记）。

4. 事件配置
	- 可开启/关闭“OnAssigned”“OnUnassigned”事件派发（用于性能优化场景）。
	- 可配置是否合并批处理事件：若开启，批处理阶段内部先收集，再一次性派发合并事件；若关闭则逐条派发。

5. 资源与安全边界
	- 不缓存外部系统“可执行状态”数据；仅缓存模块自身需要的最小集合引用，避免数据重复与状态漂移。
	- 不引入线程并发配置（需求未覆盖），假定调度在主上下文中执行。

## 二、查询功能设计

查询目标：让外部系统能清晰获知“某单位当前指派去哪里”“哪些单位空闲”“特定目标被哪些单位占用”“最近一次调度的概要结果”。所有查询均为只读；无副作用，不触发重算。

1. 单位分配状态查询
	- 输入：单位标识。
	- 输出语义：若已分配返回目标标识及相关策略标记；若未分配返回空结果。

2. 目标占用查询
	- 输入：目标（岗位 / 点位 / 资源槽）标识。
	- 输出语义：当前绑定的单位集合（顺序不保证），若无则为空集合。

3. 空闲单位列表查询
	- 语义：返回当前未被任何目标占用的单位集合；不保证稳定排序。

4. 最近调度批次摘要查询
	- 内容：本次新增分配数量、取消分配数量、跳过数量（因无策略或策略拒绝）、处理耗时区间（粗粒度，可选）。
	- 目的：便于外部做性能监控与行为验证。

5. 事件监听（间接查询）
	- 外部通过订阅 OnAssigned / OnUnassigned 获取增量变化；与主动查询互不冲突。

边界与约束：
	- 查询不会阻塞正在进行的调度（假定单线程上下文下顺序执行）。
	- 不提供历史版本或撤回机制（需求未要求）。

---
## 三、修改功能设计

修改类动作指“改变内部可调度集合或触发调度”的操作。去除多余状态，所有流程基于“当前集合 + 触发条件”直接计算，不维护复杂中间缓存。

1. 注册单位
	- 输入：单位标识及其最小必要属性集合（需求未细化属性，不扩展）。
	- 行为：放入“可调度集合”；若启用即时分配则立刻尝试分配；否则等待批处理。
	- 冪等：重复注册同一标识忽略（不抛错）。

2. 注销单位
	- 行为：若单位已分配，先执行取消分配逻辑并派发 OnUnassigned（若事件开启），再从集合移除。
	- 冪等：不存在则忽略。

3. 触发即时再分配
	- 外部显式请求时，将当前所有“无目标”或“标记为需重评估”的单位放入一次性调度流程。
	- 若配置禁止即时模式，则调用无效果（安静返回）。

4. 批处理调度周期到达
	- 定时器 / 帧计数满足阈值后执行：
	  - 收集自上次批处理以来发生状态改变的单位集合（注册、注销已在各自流程即时处理，故这里主要包含“仍未分配”与“被标记需重评估”）。
	  - 根据策略标识进行分组，按组请求策略处理（若某组无策略则直接跳过全部该组单位）。
	  - 生成分配与取消分配结果，派发事件（可合并）。

5. 取消分配（内部触发）
	- 场景：目标失效 / 单位注销 / 策略拒绝继续占用。
	- 行为：移除绑定关系，触发 OnUnassigned（开启时）。

6. 策略覆盖修改
	- 允许外部提供新策略标识与参数集合，替换原有映射；不回溯已分配结果，除非外部随后发起一次即时再分配请求。
	- 避免在所有修改路径里自动触发全量重算，减少不可控开销。

7. 事件开关修改
	- 运行期允许关闭事件派发；关闭后不追补历史事件。

一致性与约束：
	- 修改操作顺序执行，保证不会出现“一个单位同时指向多个目标”的中间状态暴露给查询层。
	- 不做“事务回滚”设计（需求未要求）；若未来需要需在需求层增加再设计。

	## 版本 1.0.2 更新说明

	为响应 1.0.2 的版本迭代，设计层作出以下调整：

	- 派遣执行模型重构：原文档中以组件形式描述的 `DispatchUnitComponent` 的职责，被重构为 `DispatchExecution` 概念；`DispatchExecution` 可实现为独立的执行实体，用于更灵活地管理派遣生命周期与并发执行。
	- 系统重命名/重构：原 `DispatchUnitSystem` 在重构后以 `DispatchExecutionSystem` 承担创建、启动、取消单个派遣执行体的职责；`DispatchStateSystem` 继续负责基于 `DispatchStateComponent` 的周期检查与规则校验。
	- 新增集合管理：引入 `UnitDispatcherListComponent`（原 `DispatchExecutionListComponent`）与配套的 `UnitDispatcherListSystem`（原 `DispatchExecutionListSystem`），用于在宿主实体上管理多个 `UnitDispatcher`（原 `DispatchExecution`）的集合（批量查询、批量取消、生命周期统一管理），降低单实体上大量执行体时的调度开销与复杂性。
	- 增强事件与契约：事件派发契约保持不变（`IDispatch` 系列接口），但建议在批量场景下优先通过 `UnitDispatcherListSystem`（原 `DispatchExecutionListSystem`）聚合事件以减少外部回调频次。

	以上改动只是设计层约定；具体实现时应遵循“向后兼容优先”的原则 —— 现有外部依赖若仍使用旧契约，应提供兼容适配层或迁移指南以避免破坏上层使用。

		## 版本 1.0.3 更新说明

		为响应 1.0.3 的版本迭代，设计层同步完成命名统一：

		- `DispatchExecution` 实体更名为 `UnitDispatcher`。
		- `DispatchExecutionSystem` 更名为 `UnitDispatcherSystem`。
		- `DispatchExecutionListComponent` 更名为 `UnitDispatcherListComponent`。
		- `DispatchExecutionListSystem` 更名为 `UnitDispatcherListSystem`。

		变更只涉及命名统一，不扩展功能与流程；若外部仍依赖旧命名，建议提供别名或迁移指引以降低升级成本。
